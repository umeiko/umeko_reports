# IID 50:50：有限算力下的补实验执行报告

更新：2026-09-10。状态：方案已设计，尚未训练。本轮不安排 143M/803M 重训补种子；原 143M、3B token、三种子大矩阵移到未来计划。

已有实验不是空白：EXPS 五档英文质量扫描已完成；集群 43M/143M 各六条件两种子的双语实验也已完成，均包含 IID 50:50。下文 E1/E2 是对已有权重补评测，Q43 是尚未见到执行产物的“英文质量×中文质量”四格桥接，不是重新证明 IID 基线存在，更不是重跑五档 Scale。完整已完成清单见 [当前进展](PROGRESS_CN.md)。

## 1. 先理解我们到底在问什么

IID 50:50 在这里表示：整次训练看到的英文和中文 token 各一半，把等长的单语言序列随机交错。它不表示每篇文章都中英对照，也不表示每一步必须恰好中英各半。实际是固定两种语言的总配额，再随机打乱标签；严格说是“无放回的随机平衡混合”，论文沿用 IID 作为简称。

现有实验发现这种喂法的内部文本预测分数最好。还缺两个回答：第一，它在真实中英阅读题上也好吗？第二，如果把英文或中文材料筛得更严格，这种双语训练会怎样变化？这两件事可以用现有模型和 43M 小模型推进。

## 2. 先跑哪几件事

## 3. E1/E2：不重训怎样补中英证据

### 3.1 阅读理解

使用 [facebook/belebele](https://huggingface.co/datasets/facebook/belebele)，冻结 revision `7899cdfa4e1e0d733fd77c848e2c273cb1d32be2`，语言 `eng_Latn`、`zho_Hans`，各 900 题。它是一段短文加一道四选一阅读题，同一道题有多语言版本。用源字段构造跨语言稳定的题 ID，并验证篇章、问题及正确选项对齐；不能只用文件行号配对。

每个模型回答全部 1,800 个语言版本，不抽“好做的题”。固定零样本模板，用题干和候选答案的条件 log-likelihood 做选择；主口径为答案长度归一化分数，同时保存未归一化分数作为敏感性结果。题目超上下文时优先截短 passage，保留问题与全部选项，记录截断比例；模板、归一化单位及截断规则在看测试成绩前冻结。

报告 EN accuracy、ZH accuracy、两边都答对比例、两边选项一致比例、EN对/ZH错、ZH对/EN错。比如“同一道题中英都答错且选同一个选项”只能计入一致，不能计入正确。900 题来自共享篇章，置信区间按对齐篇章 ID 成组抽样 10,000 次，不能当 900 个完全独立题目。

XCOPA 暂列次要可选项。官方 [cambridgeltl/xcopa](https://huggingface.co/datasets/cambridgeltl/xcopa) 不能直接假定有 `en` 配置；英文来源需回到原 COPA 并核对 ID、split、标签和许可。只有 500 个 test 项逐一核对成功才能做配对；否则只报中文单语结果，或先不跑。不得自行翻译后仍称“官方英中配对榜单”。

### 3.2 文本预测

先复用旧内部 dev/test（每语言 dev 256 个 1,024-token 块、test 512 块），用于检查重评测是否复现旧数值。新外部评测使用 `wikimedia/wikipedia`，revision `b04c8d1ceb2f5cd4588862100d08de323dccfbaa`，配置 `20231101.en` 和 `20231101.zh`，每语言最多 1,048,576 个被评分 token。按文档 SHA256 排序取样，与可用训练清单去重。若缺训练原文，只能标“重合审计未完成”。

新文档 BPB = 被评分 token 的 NLL 总和 /（同一被评分文本的 UTF-8 字节数 × ln 2）。NLL 与字节分母必须覆盖相同范围，BOS/EOS 等特殊 token 不算文本字节。短文独立计分，长文用固定 1,024 上下文、512 stride，每个目标 token 只计一次；边界映射需校验 tokenizer 解码的字节一致性。记录每篇文档 NLL、字节数、token 数；不能把“每文档 BPB 简单平均”冒充语料总 BPB。

新 BPB 与历史打包块 BPB 分栏呈现。两种分母/上下文规则未验证一致前，不比较绝对数值。主看同一个测试集上条件间的差，而不是拿中文 BPB 和英文 BPB 比谁“更难”。

E1 最小交付：3 个模型 × 2 语言 × 900 题 + 两套语言外部 BPB；E2 复用 E1 的 IID 输出，不重复计算。所有模型在同一设备/精度/评测器上比较，先做 32 项转换一致性测试，防止 checkpoint 格式转换出错。

## 4. Q43：质量实验的四组是什么

只使用 Ultra-FineWeb 的 EN/ZH 网页，暂不混入数学或合成来源，让唯一的新干预是网页筛选条件。

| 条件 | 英文 | 中文 | 固定语言比例 | 每种子训练 token |
|---|---|---|---:|---:|
| Q0 | B：上游已发布池，score ≥ 0.5 | B：同规则 | 50:50 | 100,663,296 |
| Q-EN | H：score ≥ 0.9 | B | 50:50 | 100,663,296 |
| Q-ZH | B | H：score ≥ 0.9 | 50:50 | 100,663,296 |
| Q-BOTH | H | H | 50:50 | 100,663,296 |

每组 seeds `2027, 2028`，共 8 个 run、805,306,368 个训练 token。这是小预算的机制先导，不是 20B 英文扫描的直接复现。Q0 也要新训：历史 IID 使用五个数据仓库，不能拿它作这次仅网页干预的基线。

B 本身是上游筛过的发布池，不能称“原始互联网”。[Ultra-FineWeb](https://huggingface.co/datasets/openbmb/Ultra-FineWeb) 提供中英文网页，EN 预览含 `content/score/source`。本方案复用旧冻结 revision `02c85641e3d19a854be2e09139c25adaa9518063`；开工前分别检查两种语言实际 Parquet schema 的 score、范围、缺失率。中文缺少有效分数时，先降为 Q0/Q-EN 两组 × 两种子（402,653,184 token），明确不能分析中文过滤。不得临时用生成式打分替换而不修改协议。两种语言同为 0.9 不代表语义质量已校准相等，保留率必须分别报告。

### 4.1 数据怎么取，取多少

1. 从已有 shard 清单开始。EN 首个候选 `data/ultrafineweb_en/ultrafineweb-en-part-1795-of-2048.parquet`，ZH 首个候选 `data/ultrafineweb_zh/ultrafineweb-zh-part-138-of-256.parquet`；文件 hash 与旧清单一致时可复用本地文件。
2. 候选不足时，枚举同 revision、同语言的全部 shard，以 `SHA256("iid50-quality-v1"|revision|path)` 排序依次扩展。不能按下游分数挑 shard。所有四组使用相同候选扫描范围。
3. 对规范化文本做 SHA256 精确去重；同语言近重复文档用固定 13-unit shingles、128 permutation 的 MinHash 召回，再按实际 Jaccard ≥0.8 合并。一个 unit 为一个汉字或一个小写拉丁字母数字串。近重复 cluster 必须整体分到同一 split。
4. 哈希只用 NFKC、拉丁大小写折叠和空白归一化；训练保留原文。长度限定 200–8,192 个发布版 tokenizer token；先处理基准污染候选，再分 train/dev/test。保留 direct/ambiguous 清单；无法自动判定时记录排除理由。
5. 先冻结完整候选 shard 范围，再全局去重、建 cluster 和划分；cluster ID 用成员最小 hash，`SHA256("iid50-quality-split-v1"|cluster_id) mod 10000` 的 0–49 为 dev、50–99 为 test、其余 train。之后才按训练质量阈值形成 B/H。评测集始终从共同 B 池取，不随训练过滤条件变化。如果后续发现配额不足而扩大候选范围，必须从完整候选重新生成四组和全部 split，废弃未开训的旧版本，不能增量追加后继续沿用旧 cluster ID。任何正式训练前冻结最终版本。
6. 每语言 B/H 各需至少 50,331,648 个实际训练 token，即 49,152 个 1,024-token 序列。连接文档用 EOS，丢弃末尾不足一个完整序列的余量；增加候选文档直至配额满足。B/H 可有重叠，这是嵌套过滤的自然结果；不强行做互斥池。每个条件内部无文档重复轮播，唯一文档数、唯一文本 token、EOS token 及跨条件重合比例都要登记。
7. 每语言共同 dev 目标 262,144 个被评分 token、test 1,048,576 个。只从对应 split 按独立 hash 排序取样；若不足，继续扩展候选 shard，不能复制评测文章。测试文档计分遵循上一节的独立文档 BPB，并保存文档 ID。
8. B/H 池在两个种子间固定；各 seed 内将 49,152 个 EN 标签和 49,152 个 ZH 标签随机排列，四组共享同一标签序列。对应语言条件相同时，还必须共享文档及序列顺序。例如 Q0 与 Q-EN 的中文流完全一样。

UFW 不必全量下载。若 H 过滤后的可用比例为 r，每语言至少需扫描约 50.33M/r 的合格候选 token，再加评测和去重余量。r 在本地实测，不预设“固定删掉 67%”。达到配额立即停止；当现有源不足时先报告缺口和预计额外磁盘量。

### 4.2 怎么训练

沿用 43M 架构：12 层、hidden 384、FFN 1024、6 attention heads/2 KV heads、head_dim 64、词表 64,000、tied embedding、RoPE 100,000。tokenizer 为 Haidass1.5 revision `d8a00d4943971088e6f0f4e08fb317dd5ba33ed1`。

| 设置 | 固定值 |
|---|---|
| 初始化 | 每 seed 新初始化一次，四条件复制同一权重 hash |
| 上下文 / global batch | 1,024 / 32 序列 |
| 每更新输入 token | 32,768 |
| 更新数 / 每 run | 3,072 / 100,663,296 token（包含输入 EOS；另记录被预测 token） |
| 每语言 token | 50,331,648 |
| Optimizer | AdamW，β=(0.9,0.95)，eps=1e-8，所有参数 weight decay=1e-5 |
| LR | peak 0.0015；31 步线性 warmup 后 cosine 至 0；按已有 P0 公式冻结索引 |
| clip / dropout | 2.0 / 0 |
| 精度 | FP32 主权重、AdamW 状态及参数更新；前向 AMP FP16 + loss scaling；cross-entropy/log-softmax 本身先转 FP32，再用 FP32 累加 NLL；不得只把 FP16 loss 求和转 FP32 |
| 2080 Ti 起步 | micro batch 4 × accumulation 8；OOM 则统一 2×16 |
| 4090 起步 | 同一 4×8；预跑后可统一增 micro batch，保持 global batch |
| 验证 / checkpoint | step 0 及每 192 步 dev；0/768/1536/2304/3072 保存可恢复 checkpoint；主结果用最终点 |

先做单独 200 步 dry-run，报告峰值显存、稳定吞吐、overflow、恢复后下 20 条 sequence hash。测完重新从初始化开始正式运行，不把预跑重复 token 偷加到正式预算。训练异常保留失败记录，不根据成绩挑重跑。

正式运行采用严格预算合同：3,072 次输入更新必须对应 3,072 次成功参数更新。预跑冻结 loss-scaler 配置；正式阶段任何 nonfinite/overflow 导致跳过更新，立即将该 run 标为失败并停止，保存 attempted/successful/skipped 更新及已消费 token，不自动补喂或重放数据。修复须登记协议版本并完整重启受影响的配对条件，而非只重跑分数差的一组。中断恢复必须同时恢复优化器、scaler、调度器、随机状态和数据游标；恢复不能重复消费序列。

### 4.3 看哪些指标，怎样解释

主终点是最终 checkpoint 的 EN/ZH 共同 held-out BPB，分别报告。相对 Q0 的等语言指标为：`0.5 × [(BPB_EN/BPB_Q0_EN-1) + (BPB_ZH/BPB_Q0_ZH-1)] × 100%`，越低越好。同语言、同 seed 配对；不能只报有利语言。

四组分别做固定测试集的主比较 Q-EN−Q0、Q-ZH−Q0、Q-BOTH−Q0；还计算 `Q-BOTH−Q-EN−Q-ZH+Q0` 的 BPB 差分，回答两种语言的过滤作用是否相加。因为顺序全固定为 IID，这个 2×2 **不能**证明“质量×顺序交互”。若要研究后者，需另加同质量条件下的顺序因子。

每 seed 单独报告效果，附两 seed 均值、范围和描述性样本 SD。按文档/篇章配对 bootstrap 得到的区间只表示固定权重下的测试样本不确定性，不替代训练随机性。两种子同向可称“在这两次重复中方向一致”，不能自动称统计显著。0.5% 相对 BPB 只作预先约定的实用容忍线；样本区间通过也不等于已完成跨种子的正式非劣检验。

下游用全部 Belebele 900 对，最终 8 个 checkpoint 共 14,400 个语言题版本。报告各语言准确率及 both-correct；接近随机水平时保留结果并解释测评地板效应，不偷偷换基准。主图为两语言 dev 曲线、最终逐 seed 散点、质量四格效果图、语言不对称错误表。不得训练途中反复看测试成绩选 checkpoint。

### 4.4 要多少算力

8 个 43M run 的纯训练时间 = 805,306,368 / 实测 token/s / 3,600。用三个吞吐场景估算：

| 吞吐（预算情景） | 8 run 串行纯训练 GPU 小时 |
|---:|---:|
| 2,000 token/s | 111.85 |
| 10,000 token/s | 22.37 |
| 38,000 token/s | 5.89 |

旧 2080 Ti 100M 实验的日志 median active throughput 约 38k token/s，但它是旧软件、旧评测和旧数据条件，不能承诺新实验仍达到。排队、取数、清洗、验证、checkpoint I/O、散热休眠及下游评测另计，开工预算用 200-step dry-run 的实测值外加至少 30% 运维余量。内存建议 32GB 起，磁盘依 shard 清单估算，先复用已有数据。

若只够半轮，先跑 seed 2027 的四组（402,653,184 token），完整公开四组结果；第二个 seed 有资源时补齐所有四组，不只复现赢家。143M/803M 的 20B-token 种子复跑本轮为零。

建议首批硬上限为 32 GPU 小时（这是待采用的预算方案，本轮没有启动训练）：预跑 1 小时、E1/E2 合计 7 小时、Q43 含验证与保存 24 小时。各阶段到上限就暂停并报告，不借用下一阶段额度；用预跑吞吐和 30% 余量预测无法完成时，开训前改成完整的单 seed 四组或暂缓，不能跑到一半删掉不利条件。CPU 清洗另设 24 小时墙钟和 100GB 新增磁盘的停止阈值；达到阈值先给出保留率、已扫描量和缺口。可选 B43 另需明确追加至多 8 GPU 小时，不能默认吞进主预算。用户可在开工前调整这些上限。

## 5. B43 可选：只有时间够才追加

复用 Q0 的 EN/ZH 序列多重集、两种子初始化与训练设置，新增 8 块 EZEZEZEZ，每块 12,288 条序列 = 12,582,912 token = 384 updates，共 2 run、201,326,592 token。与 Q0 比较能测网页语料上的八块代价；不能据一个块长推出“越短越好”，也不能把不同尾语言顺序当完全等价。完整块长和尾语言对照留待后续。

## 6. 集群交付与成功标准

每个 run 交付 config、code/environment revision、初始化 hash、数据清单 hash、语言标签顺序 hash、成功 optimizer update 数、实际 EN/ZH token 数、训练 loss、每次 dev、逐文档 NLL/bytes、最终逐题输出、checkpoint 路径/hash、失败/恢复记录。结果表先保留“未执行”，不能填写预期提升。

“执行完成”的标准是预算和数据合同通过、四组全部有终点评测、复现脚本能重建表图；分数变好不是完成条件。若过滤伤害中文或效果为零，也同样是论文需要报告的结果。

当前配套 [机器可读方案](IID50_PLAN.json) 是执行规格，不是现成训练器；现有脚本需新增 quality pool / 文档级评测后才能直接运行。不要把未实现的命令当可执行集群任务。
